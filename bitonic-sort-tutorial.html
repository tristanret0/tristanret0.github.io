📍 为什么 GPU 上要用 Bitonic Sort

这份教程用三个可交互组件把 bitonic sort 讲透：① 排序网络动画、② 下标位运算探索器、③ 共享内存分块图解，并衔接到你正在做的 CUDA 作业（朴素多 kernel → 共享内存双 kernel）。

核心动机：数据无关的排序网络
Bitonic sort 是一个排序网络(sorting network)：要比较哪些下标、比较多少次，完全由 n 决定，与数据的值无关。这带来两个对 GPU 极友好的性质：
  • 同一个 sub-stage 里的 n/2 个比较彼此独立 → 天然可并行；
  • 没有依赖数据的分支去决定"下一步比谁" → 控制流规整，warp 发散小。

对比作业背景里提到的朴素并行 mergesort：每轮归并活跃线程减半，最后一次归并几乎只剩极少线程在干活 —— 在 NSight 上你会看到后期 kernel 的 Achieved Occupancy 掉到个位数。而 bitonic sort 的每一个 sub-stage 都有 n/2 个比较同时进行，并行度自始至终保持饱满。代价是它做的比较更多（O(n log²n) 个比较 vs mergesort 的 O(n log n)），但在 GPU 上"规整且高并行"往往比"比较次数少但并行度差"跑得更快。

前提
经典 bitonic sort 只处理长度为 2 的幂的数组。非 2 的幂需要 padding（补到 2 的幂，填 +∞）或改用变体。

1双调序列与基本操作

1.1 什么是双调序列 (Bitonic Sequence)

一个序列如果先单调递增、再单调递减（或先减后增，又或是这种序列的循环移位），就叫双调序列。例如 [1, 4, 6, 8, 7, 5, 3, 2] 就是先升后降。

双调序列：值先升后降（先降后升、或其循环移位也算）。

1.2 双调拆分 (Bitonic Split)

对长度 n 的双调序列 L = x₀ … x₍ₙ₋₁₎，把前后两半逐位比较，拆成两个序列：

Lmin = min(x₀, x₍ₙ/₂₎), min(x₁, x₍ₙ/₂₊₁₎), … , min(x₍ₙ/₂₋₁₎, x₍ₙ₋₁₎)
Lmax = max(x₀, x₍ₙ/₂₎), max(x₁, x₍ₙ/₂₊₁₎), … , max(x₍ₙ/₂₋₁₎, x₍ₙ₋₁₎)

关键性质：Lmin 和 Lmax 各自仍是双调序列，并且 max(Lmin) ≤ min(Lmax) —— 也就是说 Lmin 里的每个数都不大于 Lmax 里的每个数。于是问题被一分为二：只要分别把 Lmin、Lmax 排好，拼起来就整体有序。

1.3 双调合并与排序 (Merge & Sort)

反复对拆分出来的子序列做 split，直到子序列长度变成 2，就得到一个完全有序的序列 —— 这就是双调合并：

BM(n) = BS(n) + BS(n/2) + … + BS(2) = O(log n)

而要从一个乱序数组开始，得先"造"出双调序列：从长度 2 的小段开始，交替按升序/降序排，拼成长度 4 的双调序列，再合并成有序的 4；如此倍增。整套下来：

BitonicSort(n) = BM(2) + BM(4) + … + BM(n) = O(log²n) 个阶段

每个阶段对 n 个元素做 n/2 次比较，所以总比较数约 (n/2)·log²n = O(n log²n)。下一节用动画把这整个过程跑给你看。

3下标的位运算

上一节动画里"谁和谁比、按升还是降"全靠两个位运算决定。这正是作业伪码的核心：

for (i = 1; i <= log2(n); i++)            // 阶段：构造长度 2^i 的有序段
  for (j = i-1; j >= 0; j--)              // sub-stage：步长 2^j
    for (k = 0; k < n; k++) {             // 遍历数组
      l = k XOR (1<<j);                    // ① 配对下标
      if (l > k) {                         // 只处理较小的一端，避免重复比较
        if ((k & (1<<i)) == 0)             // ② 方向：bit i 为 0 → 升序
          compare_exchange_ascending(k, l);
        else
          compare_exchange_descending(k, l);
      }
    }
  • ① 配对：partner = k XOR 2^j —— XOR 把下标的第 j 位翻转，等价于"跨步 2^j 找对象"。例：BM(8) 的 j=2(步长4)，0↔4, 1↔5, 2↔6, 3↔7。
  • ② 方向：k & 2^i —— 看下标的第 i 位。为 0 的那批（"偶块"）按升序、为 1 的（"奇块"）按降序，于是每 2^i 个元素拼成一个长度 2^{i+1} 的双调序列，供下一阶段用。

4CUDA 朴素实现

把伪码直译成 CUDA：用 <<<blocks, threads>>> 启动一大批线程，一个线程负责一个下标 k 的比较交换。

bitonic_naive.cu
// 一个 sub-stage 一个 kernel：每个线程处理下标 k
__global__ void bitonicStep(int* a, int n, int i, int j) {
    int k = blockIdx.x * blockDim.x + threadIdx.x;   // 全局线程 = 下标
    if (k >= n) return;
    int l = k ^ (1 << j);                            // ① 配对
    if (l > k) {                                     // 只让较小端比较，避免重复
        bool up = ((k & (1 << i)) == 0);             // ② 方向
        if (up ? (a[k] > a[l]) : (a[k] < a[l])) {    // compare-exchange
            int t = a[k]; a[k] = a[l]; a[l] = t;
        }
    }
}

// host 端：双重循环，每个 (i,j) 启动一次 kernel
int threads = 256, blocks = (n + threads - 1) / threads;
for (int i = 1; i <= log2n; i++)
    for (int j = i - 1; j >= 0; j--)
        bitonicStep<<>>(d_a, n, i, j);   // ← 一次 launch
为什么必须启动这么多次 kernel？
sub-stage 之间有依赖：步长 2^j 这一步必须等步长 2^{j+1} 全部写完才能开始。但 CUDA 没有跨 block 的全局 barrier —— __syncthreads() 只能同步一个 block 内的线程。要让所有线程在两个 sub-stage 之间对齐，唯一办法就是结束当前 kernel、再启动下一个：kernel 边界 = 一次全局同步。
朴素版的痛点（NSight 会点名）
  • kernel launch 次数 = O(log²n)：n=100M 时 log₂n≈27 → 约 27·28/2 = 378 次 launch，开销累积。
  • 每次 launch 只做一次比较就把整个数组读一遍写一遍 global memory → 算术强度极低、memory-bound。
  • NSight 会提示 "low compute throughput and memory bandwidth utilization"。
注意：朴素 bitonic 的 occupancy 其实不低（每步约 n/2 线程活跃）；真正的瓶颈是反复的全局内存往返和 launch 次数 —— 这正是下一节共享内存优化要解决的。
Quiz · CUDA 朴素实现
朴素实现为什么要把每个 sub-stage 拆成单独的 kernel launch？
  • A.因为 sub-stage 间需要全局同步，而 CUDA 跨 block 的全局 barrier 只能靠"结束并重启 kernel"实现
  • B.因为一个 kernel 最多只能用一个线程
  • C.因为 GPU 不支持循环
  • D.这样可以减少全局内存访问
A。__syncthreads() 只同步单个 block；要让所有 block 对齐到下一 sub-stage，只能用 kernel 边界做全局同步。这反而增加了 global 访问与 launch 开销（D 正好说反了）。

5共享内存优化

朴素版的病根：每个小 sub-stage 都单独 launch、都把整个数组在 global memory 里读写一遍。关键观察：当步长 2^j 小到一对元素都落在同一个 block 的 tile（T 个元素）内时，这一串连续的小步长 sub-stage 完全可以在 shared memory 里连做 —— 加载一次、用 __syncthreads() 在块内同步、做完再写回一次。

把 kernel 拆成两个
  • shared kernel：处理步长 < tile 的一串小 sub-stage —— 一次 global 读 + 块内多步 + 一次 global 写。
  • global kernel：处理步长 ≥ tile 的大 sub-stage（配对元素在别的 block，必须走 global）。
bitonic_shared.cu（策略级，简化为每线程 1 元素）
// shared kernel：把块内一串小步长 (jStart..0) 一次性做完
__global__ void bitonicShared(int* a, int n, int i, int jStart) {
    extern __shared__ int s[];
    int t = threadIdx.x, base = blockIdx.x * blockDim.x;
    s[t] = a[base + t];          // ① 协作加载一次（合并访问）
    __syncthreads();
    for (int j = jStart; j >= 0; j--) {     // ② 块内连做，不重启 kernel
        int l = t ^ (1 << j);
        if (l > t) {
            bool up = (((base + t) & (1 << i)) == 0);
            if (up ? (s[t] > s[l]) : (s[t] < s[l])) { int tmp=s[t]; s[t]=s[l]; s[l]=tmp; }
        }
        __syncthreads();          // 块内同步即可，无需 kernel 边界
    }
    a[base + t] = s[t];           // ③ 写回一次
}

// host：大步长走 global kernel，步长一旦落入 tile 内就交给 shared kernel 收尾
for (int i = 1; i <= log2n; i++) {
    for (int j = i - 1; j >= 0; j--) {
        if ((1 << j) >= TILE)                       // 跨 block
            bitonicGlobal<<>>(d_a, n, i, j);
        else {                                      // 步长 < tile：一次 shared kernel 收尾
            bitonicShared<<>>(d_a, n, i, j);
            break;                                  // 这一串小步长已在块内做完
        }
    }
}
还要注意
合并访问 (coalescing)：加载/写回时让相邻线程访问相邻地址，吃满带宽（冲 ≥75% throughput 的关键）。Bank conflict：shared memory 分 32 个 bank，注意访问步长避免多个线程撞同一 bank。实战常让每线程处理 2 个元素把 tile 扩到 2·blockDim，进一步减少 launch。

为什么用 shared memory 能同时减少 global 访问和 kernel launch 次数？
  • A.因为 shared memory 容量比 global memory 大
  • B.把一串小步长 sub-stage 在 block 内用 __syncthreads() 连做：数据只从 global 读一次写一次，且块内同步无需重启 kernel
  • C.因为 shared memory 完全不需要同步
  • D.因为它把排序交给了 CPU
B。一次加载进 shared，块内连做多个小步长（靠 __syncthreads() 同步，不必结束 kernel），最后写回一次 —— 既省了反复的 global 往返，又把多次 launch 合并成一次。shared memory 其实更小（A 错），块内仍需同步（C 错）。

6性能与 profiling

作业用 NSight Compute (ncu) 卡两个硬指标，先搞清它们的含义：

6.1 关键指标

指标含义作业目标
Achieved Occupancy每个 SM 上活跃 warp 数占理论峰值的百分比，反映并行度是否填满≥ 65%
Memory Throughput占峰值显存带宽的百分比。bitonic 是 memory-bound，这个越高越好≥ 75%
Warp Divergencewarp 内线程因分支走不同路径而串行化的程度；越低越好越低越好
meps每秒处理的百万元素数 = n / 总时间≥ 1000（H100, 100M）

6.2 怎么用 ncu 取数

# Achieved Occupancy
ncu --metrics sm__warps_active.avg.pct_of_peak_sustained_active \
    --print-summary per-gpu ./a.out 10000000

# Memory Throughput
ncu --metrics gpu__compute_memory_throughput.avg.pct_of_peak_sustained_elapsed \
    --print-summary per-gpu ./a.out 10000000

# 还可看：global/local 访问、分支发散
ncu --metrics l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum,\
smsp__thread_inst_executed_per_inst_executed.ratio ./a.out 10000000
调优直觉
bitonic 是 memory-bound：先保证合并访问把 throughput 顶上 75%+；occupancy 不够就调 block 大小 / 每线程元素数；shared kernel 把多步合并能同时改善两者。多个 kernel 时作业取平均。
Quiz · 性能指标
"Achieved Occupancy" 衡量的是什么？
  • A.kernel 运行了多少毫秒
  • B.每个 SM 上活跃 warp 数占理论峰值 warp 数的比例
  • C.用了多少 GB 显存
  • D.host 与 device 之间的数据传输速度
B。Occupancy = 实际活跃 warp / 理论最大 warp（占峰值百分比），反映 SM 的并行度被填满的程度。它不是时间、显存用量或传输速度。朴素 mergesort 后期因活跃线程锐减导致 occupancy 崩塌，正是本教程开篇的对比点。
